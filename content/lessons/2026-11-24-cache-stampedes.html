Cache stampedes and request coalescing

A hot key expires. For the next δ seconds, every reader misses and goes to the origin. With an arrival rate λ on that key and a recompute time δ, the origin takes roughly λ·δ concurrent requests for one value. A cache that is meant to protect the origin can end up overloading it.

concurrent origin hits at expiry ≈ λkey × δrecompute   // e.g. 50 req/s × 0.5 s ≈ 25 (Fastly's example)
The real problem

What scale forced the design

Facebook's memcache tier, described in the 2013 NSDI paper, handles billions of requests per second and holds trillions of items. They hit two related failures on keys with heavy read and write traffic. One was stale sets, where a slow writer puts an outdated value back into the cache. The other was thundering herds, where every reader that misses goes to MySQL at once. Their fix was leases. On a miss, memcached gives the client a 64-bit token, and only the holder of that token may set the value. To stop herds, each server hands out a token only once every 10 seconds per key. Other readers are told to wait briefly and retry, and by then the value is usually in the cache.

The same problem appears at the CDN layer. Cloudflare's write-up starts from an image service that gets 10 req/s while its origin can serve 1. When the cached copy expires, all 10 go through. Cloudflare's cache lock sends the origin one request at a time per asset, and concurrent misses in a data centre wait for that response. Fastly calls its version a waiting list. CloudFront says it pauses simultaneous requests that share a cache key and fans out the first response to them.

The concept

Four ways to stop the herd, and how each one fails

All four do the same thing: they decouple reader concurrency from origin concurrency for one key. They differ in who pays the latency, what correctness you give up, and which new component can break.

Two more points. Synchronised expiry is a separate trigger. A deploy that flushes the cache, or a batch warm-up, gives thousands of keys the same expiry time. Per-key locks don't help there, but TTL jitter does. And collapsing happens per collapsing point. Forty app tasks with in-process single-flight still send up to 40 fetches per key, so you need a shared layer (Redis lock, CDN shield) as well. Fastly's clustering plus shielding gives up to four collapsing points per object.

Solve it

The flash sale

An online shop serves product pages from 40 identical app servers behind a load balancer. Prices and stock come from a shared pricing service and are cached under a key like product:{id}:price with a 15-minute TTL. The pricing service is the fragile part. Its limits:

  • It handles about 50 requests/s. Above that it starts returning errors, and repeated overload makes it shed load for 10 minutes.
  • A price lookup takes p50 1.2 s and p99 6 s. You give up after 8 s.

At 20:00 a "flash sale" notification goes out. Traffic jumps to about 500 page views/s for 30 minutes, spread over roughly 2,000 distinct products with a long tail. The 20 hottest products take 40% of traffic. To make it worse, a release went out at 19:55 and its deploy script flushed the cache.

Design the read path for prices so the pricing service never sees more than 50 req/s, page p95 stays under 1.5 s, and a pricing outage degrades the page instead of breaking it. State what you would do inside one server, across the cluster and at the pricing-service boundary, and what is allowed to be stale.

Hint 1: Size the two herds separately

Per-key herd: the top products get about 500 × 0.4 / 20 = 10 req/s each. With δ ≈ 1.2 s that is about 12 concurrent misses per hot key, times 40 servers if each collapses only locally. Synchronised herd: after the flush, all 2,000 keys are cold at 20:00 and are all warmed within seconds, so they expire together at 20:15. Even perfect single-flight means 2,000 fetches against 50 req/s, which is 40 s of backlog.

Hint 2: Separate "show a price" from "charge a price"

A product page can tolerate a price that is a few minutes old. Checkout cannot. That split tells you where stale-while-revalidate is safe and where you need a live re-check.

Hint 3: Who is allowed to call the pricing service?

If any request path can call it directly, the 50 req/s limit is only enforced by hoping. Consider a single admission point that every fetch, foreground or background, has to pass.

Reveal model answer
  1. Collapse in two tiers. Inside each server, keep a map of in-flight fetches per key so 12 concurrent local misses become 1. Across servers, take a short-lived lock in the shared cache with a compare-and-set, such as SET lock:{key} {token} NX PX 10000. Make the lock's lifetime longer than the 8 s timeout so a slow fetch doesn't let a second one start. Losers wait briefly with jitter, for at most about 1 s, then fall back to a stale value or a "checking price" placeholder. Release with a compare-and-delete on the token, so a holder that outlived its lock can't delete someone else's.
  2. Soft and hard TTL with stale-while-revalidate for pages. Store {price, fetchedAt, softExp, hardExp, delta}, for example soft 15 min (±15% jitter) and hard 2 h. Between soft and hard, serve the cached price and queue a refresh. This keeps p95 at cache latency even when the pricing service is at p99.
  3. Refresh before expiry on hot keys. Apply the XFetch test with the stored delta on reads. That gives early, decorrelated refresh for hot keys at no coordination cost, and keeps them from ever reaching the soft TTL.
  4. One admission point for the pricing service. No request path calls it directly. Foreground misses and background refreshes all go through a shared token bucket, or a refresh queue keyed by cache key so duplicates collapse. Run it below the limit, around 45 req/s, and give interactive cold misses priority over background refreshes. When the bucket is empty, serve stale. If there is no stale value, render the page without that price.
  5. Never mass-flush on deploy. Change the key prefix only when the stored format changes. If you must start cold, pre-warm the top N keys by traffic from yesterday's logs through the same rate-limited queue, spread over minutes.
  6. Make failure cheap. Cache errors and "not available" results as negative entries with a short TTL (30–60 s) so a failing service doesn't get called on every page view. Put a circuit breaker on errors and timeouts that switches the path to stale-only. Serve stale on error.
  7. Live re-check at checkout. When the shopper presses "Buy", make one fresh, uncached price call for that single item, protected by an idempotency key. Show a price-change notice if it moved. This is the one place where staleness is not acceptable, and its volume is small.

Check the numbers. With 2,000 keys and jittered soft TTLs of 12.75–17.25 min, steady-state refresh is about 2,000 / 900 s ≈ 2.2 req/s on average, far under 50. The flush backlog of 2,000 fetches at 45 req/s drains in about 44 s while pages show a placeholder for cold tail products. The 20 hot keys get prioritised and are warm in under a second.

In practice

Where these ideas show up in real tools

Application frameworks

Many web frameworks ship a "serve stale while refreshing" cache helper and an atomic lock. Prefer those over hand-rolled code. Wrap the miss in the lock, wait only a short time, and fall back to the stale value if the lock isn't free.

In-process single-flight

const inflight = new Map();
function once(key, fn) {
  if (inflight.has(key)) return inflight.get(key);
  const p = fn().finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}

The idea works in any language: one map of in-flight work per process. It only collapses requests inside one server, so layer a shared lock behind it, and release the lock with a compare-and-delete on the token.

Databases as caches

If a database holds the cached value, store the soft expiry and the recompute time in the row. Built-in expiry jobs usually run on a schedule, often about once a minute, so don't rely on them for freshness. Check the soft expiry in code.

Queues and logs

Send refreshes through a queue keyed by cache key, so duplicates land together and a consumer can drop one when the stored value is already newer. Cap load on the backend with consumer concurrency plus a shared token bucket, not with the number of partitions.

CDNs and load balancers

Many CDNs already collapse simultaneous requests for the same cache key. Headers such as private, no-store or max-age=0 can turn that off, so check what your API sends. The number of app servers sets how wide the local fan-out is.
