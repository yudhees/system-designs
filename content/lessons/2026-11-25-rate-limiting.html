System Design Lab — Rate Limiting (2026-11-25)
System Design Lab · 25 Nov 2026 · Rate limiting

Counting requests across a fleet without letting 2× the limit through

Cloudflare had to enforce per-IP limits for millions of domains from every edge server at once. Stripe had to stop one customer's script from degrading the API for everyone. Both ended up with approximate, cheap counters in a shared store, and both chose them over exact ones on purpose.

The problem at scale

Cloudflare. Edge nodes run NGINX in each PoP. A central counter store was ruled out for latency and availability, so each PoP keeps counters in a memcache (Twemcache) cluster behind Twemproxy, which spreads keys with consistent hashing. The store only had GET, SET and atomic INCR. CAS was rejected because under attack contention most CAS transactions would fail. Increments are asynchronous, and once a client is over the limit a mitigation flag with a known expiry is cached in memory on every server, so blocked traffic stops touching the store.

Stripe. A layered set of four limiters on Redis: a per-user token bucket request-rate limiter that allows short bursts, a concurrent-requests limiter (e.g. 20 in flight) for expensive endpoints, and two load shedders keyed on traffic class rather than user. They dark-launched each limiter to see what it would block, put them behind feature flags, and made them fail open, so a Redis failure never takes the API down.

The concept

Three counters, three failure modes

A rate limiter answers one question per request: has this key used more than L units in the last W seconds? The exact answer needs a log of every timestamp (O(L) memory per key). Production systems approximate it.

AlgorithmState per keyBehaviourFailure mode
Fixed window1 counterReset to 0 at each window boundaryBoundary burst: L at 0:59 plus L at 1:00 lets 2L through in two seconds
Sliding window counter2 countersWeights the previous window by how much of it still overlapsAssumes the previous window's traffic was uniform; small over/undershoot (Cloudflare measured 6% average error)
Token buckettokens + last refill timeRefills at L/W per second up to capacity B; each request spends oneBy design admits a burst of B on top of the sustained rate; read-modify-write must be atomic
rate ≈ prev_count × (W − elapsed) / W + curr_count Cloudflare's example: limit 50/min, 15 s into the minute, prev = 42, curr = 18 rate = 42 × 45/60 + 18 = 49.5 → the next request trips the limit

The distributed part is the hard part. Every algorithm above is trivial in one process. Across N stateless tasks behind a load balancer you either share state (Redis or memcache round trip per request, plus a decision about what happens when it is down) or keep it local. Local counters with the full limit admit up to N×L. Local counters with L/N are only right if the balancer spreads one key evenly, which a single hot client never gets.

What to look for. On Window edge with one node, the fixed window's peak goes to about 2.0×L while the sliding counter stays near 1.0–1.1× and the token bucket admits only its burst B plus the L/60 refill during the attack. Under sustained overload the bucket's trailing count tops out near L+B. Switch to Per node, L with 4 nodes and every line climbs toward 4×L. Per node, L/N roughly holds the line for random routing but under-admits when nodes see uneven load, which is why Cloudflare and Stripe pay for the shared store.

Solve it

The concert-night route quota

A ride-hailing app asks a third-party maps provider for driving routes and arrival times. The provider's contract allows 50 requests/second across your whole account and suspends your key for an hour after repeated 429s. The routing service runs as app servers that autoscale from 4 to 24. The same provider also prices every trip request, a call that carries revenue, while the "car is 4 minutes away" estimate on the map is nice to have. Last Friday a concert ended, riders opened the app all at once, servers scaled out, each server's in-process limiter allowed 50 rps, and the provider suspended the key mid-evening. Trip requests started failing too.

Design question

  • Where does the limit state live, and what algorithm do you use?
  • How do you guarantee trip requests still get through when map estimates saturate the quota?
  • What does an estimate request do when it can't get a token, and what happens if the shared store is unreachable?
Hint 1: count the right thing

The limit belongs to the provider, not to your riders. Key the limiter on the provider and credential, not on caller IP, and enforce it on the outbound path. Per-server limits are the "Per node, L" mode from the simulator: N servers, N×L.

Hint 2: Stripe's load shedder

Stripe reserves a slice of capacity for critical methods. Apply the same idea to the provider: two classes of traffic, one quota.

Hint 3: failing open is not always right

Stripe fails open because blocking its own customers is worse than briefly overrunning its own capacity. Here, overrunning means a provider ban. Which way should this limiter fail?

Model answer
  1. Shared token bucket in a fast shared store, key rl:maps-provider, rate 50/s, capacity ~50 (one second of burst, matching how providers usually meter). Read-refill-spend runs as one atomic script so it is safe across 24 servers. Leave headroom: target 45/s, since the provider's clock and window are not yours.
  2. Reserve capacity for trip pricing. Two buckets that share the quota: estimates may only spend down to a floor (e.g. they get 40/s), pricing draws from the full 50. Equivalent: one bucket, and estimate requests are rejected when tokens < reserve.
  3. Cut round trips with leases. Each server takes tokens in small batches (e.g. 5 at a time) and spends them locally. Lease size bounds the overshoot to roughly servers × lease, so keep it small.
  4. No token, no provider call. Serve a recent cached estimate with a stale flag, or show a rougher estimate computed locally. Do not queue estimate work: the rider has moved on by the time it runs. Pricing calls may wait briefly (bounded, e.g. 300 ms) for a token.
  5. Fail closed to a conservative local limit. If the shared store is unreachable, each server falls back to floor(45 / expected_max_servers) rps from an in-process bucket, the "Per node, L/N" mode: it under-admits, but it cannot get you banned. Alert on it.
  6. Respect the provider's signal. On a 429 or Retry-After, write a cooldown flag to the shared store with that TTL so every server backs off at once, the same trick Cloudflare uses with its cached mitigation flag.
  7. Dark launch it: log would-be rejections for a week before enforcing, then turn it on behind a flag.
-- KEYS[1]=bucket  ARGV: rate/s, capacity, now_ms, want, floor
local b = redis.call('HMGET', KEYS[1], 't', 'ts')
local rate, cap, now, want, floor = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4]), tonumber(ARGV[5])
local t  = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
t = math.min(cap, t + (now - ts) / 1000 * rate)
local granted = 0
if t - want >= floor then t = t - want; granted = want end
redis.call('HSET', KEYS[1], 't', t, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return granted   -- estimates: floor = reserve; pricing: floor = 0

Use the store's own clock rather than each server's clock if server clocks may drift; passing now in keeps the example short.

In practice

Where these ideas show up in real tools

Web frameworksBuilt-in rate-limit middleware usually keeps a hit counter with a decay timer in your cache, which behaves like a fixed window. That's fine for login and one-time-code abuse. For partner-facing quotas, use a shared store and an atomic token bucket like the one above.
Outbound HTTP clientsPut the limiter in the client wrapper for each provider, not in route middleware. Batch token leases per server so a request that fans out to 30 providers doesn't cost 30 round trips to the shared store.
DatabasesKeep hot counters out of them. A per-request increment on one row or document is a write hotspot. A database is the right place for the limit configuration per partner and provider, loaded into the shared store or memory.
Queues and logsRate-limit consumers, not producers. A consumer that pushes notifications to a partner can pause its partitions when that partner's bucket is empty and resume later. Lag grows instead of 429s, and lag is something you already alert on.
API gateways and edge rulesGateway throttling is usually a token bucket (steady rate plus burst) that returns 429, and some providers document it as best-effort, a target rather than a guaranteed ceiling, so keep your own limiter for contractual limits. Edge rate rules work per IP, the Cloudflare-style first line.
AutoscalingAutoscaling changes N under you. Any per-server limit has to be derived from the maximum server count, or it silently grows the effective limit on every scale-out.
