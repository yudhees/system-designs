Consistent hashing, virtual nodes and bounded loads

How to spread keys over a changing set of cache or storage nodes so that adding a node moves about 1/N of the data instead of nearly all of it, and how to stop one popular key from melting the node that owns it.

The real-world problem

Vimeo, 2016. Skyfire, Vimeo's video-packaging layer, serves almost a billion DASH and HLS requests a day. It used consistent hashing to route requests for a given video to the same servers so local caches stay warm. But popularity is skewed: every request for a viral video lands on the same few servers, which overload. During peaks each shared memcached server pushed about 400–500 Mbit/s outbound (about 8 Gbit/s total). Andrew Rodland implemented Google's consistent hashing with bounded loads in HAProxy (accepted in 1.7.0-dev5, stable in 1.7.0). Afterwards the memcached servers sat comfortably below 100 Mbit/s each, and Google reports cache bandwidth fell by almost a factor of 8.

Discord, 2017. Discord routes each guild to the node that owns it with a consistent hash ring, and every session looks up the node for each guild it belongs to (about 5 on average), with up to 500,000 sessions per Erlang VM. The ring was on the hot path: a restarting session server spent about 30 s just on ring lookups. Moving the ring into ETS cut that to 17.5 s, and compiling it into a read-only module (FastGlobal) brought a lookup to about 0.3 µs and the total to 750 ms. Bursts of reconnects had also overloaded the single process that served the ring.

Amazon Dynamo, 2007. Dynamo's paper names the two flaws of the basic ring: random node positions give non-uniform data and load distribution, and the ring ignores node heterogeneity. Virtual nodes fix both. Its production measurements showed load imbalance up to 20% at low load and close to 10% at high load. With random tokens (strategy 1) bootstrapping a new node took almost a day; fixed equal-sized partitions (strategy 3) balanced best and cut per-node membership state by three orders of magnitude.

The concept

Naive: hash(k) mod N. Balanced, stateless, and catastrophic on resize. Going from N to N+1 nodes changes the owner of about N/(N+1) of keys, so adding a 9th cache node misses about 89% of the cache at once. The whole working set refills from the origin, which for us means the suppliers.

Ring. Hash nodes and keys into the same 32-bit space and give each key to the first node clockwise. A membership change only moves keys in the arcs next to the node that changed, about 1/N of keys in expectation.

Virtual nodes. With one point per node, arc lengths vary a lot, so some nodes own several times the average. Putting V points per node smooths it: imbalance shrinks roughly with 1/√V. When a node dies, its load spreads across all survivors instead of falling on one neighbour. Weighting V per node handles mixed instance sizes.

Bounded loads (Mirrokni, Thorup, Zadimoghaddam). Even a perfect key split fails when traffic per key is skewed. Cap each node at ⌈c · average load⌉. A key whose natural owner is full walks clockwise to the next node with spare capacity. Every node is guaranteed to stay ≤ c × average, and each insert or removal moves O(1/ε²) other keys, where c = 1+ε. Vimeo's write-up suggests c between 1.25 and 2.

Solve it: supplier-rate cache during a Diwali peak

Your meta-search caches supplier availability and rates in 8 Redis nodes (not Redis Cluster, plain instances behind the app) keyed by rate:{hotelId}:{checkin}:{nights}:{occupancy} and picked with crc32(key) % 8. The hit rate is 92%. On a festival weekend, Fargate scaling adds a 9th cache node and a 9th search worker. Within a minute, supplier calls spike about 10×. Two suppliers start returning HTTP 429, and search p99 goes from 900 ms to 6 s. At the same time, one Goa resort and a handful of Mumbai hotels get 30% of all lookups, and the node that owns them hits its CPU limit.

Redesign key placement so that (a) scaling the cache tier doesn't cause a supplier storm, (b) hot hotels can't overload one node, and (c) booking events stay ordered per booking in Kafka when you add partitions.

Hint 1: Do the remap arithmetic

Going from 8 to 9 nodes under mod N moves about 8/9 ≈ 89% of keys. Your effective hit rate collapses from 92% to around 10% instantly, and every miss is a supplier call.

Hint 2: Key count isn't load

Vnodes balance keys. The hot-hotel problem is request weight per key. You need a load-aware rule (bounded loads), key replication for the very hottest keys, or both.

Hint 3: Kafka doesn't rehash for you

The default partitioner is murmur2(key) % numPartitions. Kafka's docs say adding partitions doesn't change the partitioning of existing data and that Kafka won't redistribute data automatically, so new events for an existing booking can land on a different partition than its earlier events.

Show model answer
  • Placement: replace % N with a ketama-style ring (100–200 vnodes per node, weighted by instance size) or move to Redis Cluster's 16384 hash slots. Adding the 9th node now moves about 1/9 of keys, taken evenly from all 8 nodes. Better still, pre-split: run more, smaller logical shards than you need and move slots, not keys.
  • Warm-up: treat cache resizes as deploys. Add the node to the ring with low weight and ramp it up, or dual-read from old and new owners for one TTL window. Keep a stale-while-revalidate copy so a miss doesn't have to call the supplier.
  • Supplier shield: coalesce in-flight misses per key (single-flight) and put a per-supplier token bucket in front of fan-out, so a cold cache degrades latency instead of tripping 429s. This connects to the earlier labs on stampedes and rate limiting.
  • Hot hotels: route with bounded loads (c ≈ 1.25) at the routing layer, so overflow spills to the next ring node. For the top few keys, also replicate: write rate:{id}#r0..r3 and read a random replica, or keep a 1–5 s in-process L1 cache in each search worker. Detect hot keys from request counters, not by guessing.
  • Kafka: key booking events by bookingId. Size partitions for peak at creation, since adding partitions breaks per-key ordering. If you must grow, create a new topic with more partitions, dual-write, drain the old topic, then cut consumers over. Consumers stay idempotent on (bookingId, eventSeq) so the overlap is harmless.
  • Trade-off to state: bounded loads and replicas reduce cache affinity, so hit rate dips slightly when spill happens. You accept that in exchange for a hard ceiling on any one node.

Apply to your stack

Laravel cache

With the memcached driver, set Memcached::OPT_LIBKETAMA_COMPATIBLE => true in config/cache.php options to get ketama consistent hashing instead of modulo. With Redis Cluster, keep related keys together with hash tags, e.g. rate:{htl_123}:…, so multi-key ops stay on one slot.

Node.js routing

For sticky routing of supplier connectors or per-hotel workers, keep a sorted array of vnode hashes and binary-search it. Rebuild it only on membership change and publish it read-only, as Discord learned. Never compute the ring per request.

MongoDB

Use a hashed shard key for monotonically increasing fields (ObjectId, timestamps) to avoid a single hot chunk. Ranges then become broadcast queries, so for availability lookups prefer a compound key such as { supplierId: 1, hotelId: "hashed" }: equality targeting and zones on the prefix, even spread on the hash.

Kafka

Partition count is part of your key → partition contract. Over-provision partitions at topic creation for booking and webhook topics, key by the entity whose ordering matters, and treat repartitioning as a migration, not a config change.

AWS Fargate

Autoscaling changes membership often. Any tier that keys state to task identity (in-memory caches, sticky consumers) needs ring placement plus a warm-up ramp, or scale-out events will look like cache flushes.
