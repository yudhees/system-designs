System Design Lab — Idempotency Keys (2026-11-27)
System Design Lab · 27 Nov 2026 · Idempotency

Retry without paying twice

Your API charged the shopper's card. The response died on the way back. The app retries. Did they just pay twice?

TL;DR

Networks lose responses, so clients must retry. Retrying is only safe if the server can tell "this is the same request again" from "this is a new request".

The client sends a unique idempotency key with each operation. The server claims the key and the work atomically, saves the result, and replays that result for every retry.

The real-world problem

Airbnb's payments split into services, and retries got dangerous

What happened

Airbnb was moving payments from a monolith to a service-oriented architecture (SOA). Every payment now crossed several network hops, and each hop could time out.

What broke

A timed-out call is ambiguous. The charge may or may not have happened. Retrying blindly risks a double payment, and not retrying risks a lost one. Airbnb said they "couldn't compromise on data consistency".

What they changed

They built Orpheus, one shared idempotency library. Every request runs in three phases: Pre-RPC (record the request in the DB), RPC (the network call only), Post-RPC (record the response). There is no network call inside a DB phase and no DB work inside the RPC phase.

What improved

Airbnb reported five nines in consistency for payments, while annual payment volume doubled.

Real numbers · Stripe API v1

Keys are up to 255 characters. Stripe saves the status code and body of the first request, including 500 errors, and replays it. Keys can be pruned once they are at least 24 hours old. After that, the same key creates a new request.

The concept

A cloakroom ticket for your request

Without a ticket

You hand over your coat. The attendant turns away, and you aren't sure they took it, so you hand over a second coat. Now two coats are hanging under your name.

With a ticket

You write ticket #A7 first. If you are unsure, ask again with #A7. The attendant says "#A7 is already hanging" and hands you the same receipt.

  • Idempotent: doing it once or ten times leaves the same state. GET and DELETE already behave this way. POST /orders does not.
  • Idempotency key: a random ID the client creates once per intent (Stripe suggests a V4 UUID) and resends unchanged on every retry.
  • Claim: the server's atomic "insert this key or tell me it exists", usually a unique index.

The three ways a call fails (Stripe's list)

Key idea

Recording the key and doing the work must succeed or fail together. AWS says this must be an ACID operation. Otherwise you get a key with no order, or an order with no key.

Gotchas
  • Same key, different body. AWS returns a parameter-mismatch validation error. Brandur's Postgres design returns 409. Never replay a response for a different request.
  • A stuck "in progress" key. If the server dies mid-request, the key stays locked. Orpheus gives each lease an expiry, so a retry is allowed only after the lease runs out.
  • Replica lag. Orpheus always reads idempotency rows from the primary. A replica may not have the first response yet.
  • Downstream calls. A charge at a payment provider or a call to a partner API is a "foreign state mutation" that you can't roll back. Give it its own derived key.

Solve it

One order, four ways to duplicate it

Scenario. A shopper pays for an order in your mobile app. Your API (1) charges the card with the payment provider, (2) asks a partner's fulfilment API to create the shipment, and (3) publishes order.confirmed to a message queue for emails and invoices.

The fulfilment API has no idempotency support and sometimes times out after it has already created the shipment. The mobile app retries on timeouts. Servers get stopped during deploys.

Design it so that no shopper is charged twice, no shipment is created twice, and no confirmation email goes out twice.

Hint 1: where does the key come from?

Generate it on the device when the checkout screen opens, not per HTTP attempt. A double-tap and a retry must carry the same key.

Hint 2: the partner can't dedupe for you

Send the partner your own unique reference. After a timeout, look the shipment up before you retry.

Hint 3: think in phases

Each external call is its own step. Save a recovery point after every one, so a restarted server knows where to resume.

Reveal the model answer
  • Client: UUID v4 per checkout, sent as Idempotency-Key. Retry with exponential backoff + jitter.
  • Claim: insert {userId, key, requestHash, status: started, lockedUntil} under a unique index on (userId, key), in the same transaction that creates the pending order.
  • Existing key: finished with the same hash → replay the stored code and body. Lease still active → 409 + Retry-After. Different hash → reject as a mismatch.
  • Payment charge: pass a derived key such as order-{id}-charge, so the provider dedupes your own retries. Save recovery_point = charged.
  • Fulfilment partner: send clientRef = order-{id}. On timeout, mark the order unknown, then look the shipment up by reference before creating it again. Never retry blindly.
  • Events: write order.confirmed to an outbox in the final transaction. The email consumer dedupes on event ID with a unique index, because redelivery will happen.
  • Recovery: a completer job picks up keys whose lease expired mid-flow and resumes from recovery_point. A reaper deletes keys after ~24–72 h.
  • Reads: read key rows from the primary, never a lagging replica.
In practice

Where this lives in real code

Web frameworks

Write one idempotency middleware that claims the key inside a database transaction, stores the response after the handler runs, and replays it on a repeat. A cache lock alone can expire mid-request, so the stored row is the real guard.

Any language

The same middleware works in every stack. Insert the key row and treat a duplicate-key error as "this key already exists", then branch on its status.

Databases

A unique compound index on (user, key) is the atomic claim. A scheduled cleanup or expiry index is the reaper. Read key rows from the primary.

Queues and logs

Producer idempotence only stops duplicate writes from producer retries. Consumers still see redelivered messages after rebalances, so keep a processed-event-ID table in the consumer.

Deploys and autoscaling

Servers stop during deploys and scale-in, so any request can die halfway. Lease expiry plus a scheduled completer job turns "stuck" into "resumed".

Remember this

  • A timeout means "unknown", not "failed". Retries are mandatory, so make them safe.
  • The client creates the key once per intent and resends it unchanged on every retry.
  • Claim the key atomically with the work, then store and replay the response, errors included.
  • External calls get derived keys or lookup-by-reference. Expire stuck leases and resume from recovery points.
